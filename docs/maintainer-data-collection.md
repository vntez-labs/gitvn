# Maintainer evidence collection

## Verified API behavior

- GraphQL `PullRequest` exposes nullable `author`, `mergedBy` and `mergedAt`, along with `merged`, `reviews` and `closingIssuesReferences`. The first two actors are interfaces; eligibility requires `__typename: User` and a stable user ID. A closing reference is a candidate for closure, so the collector checks the issue's latest `ClosedEvent.closer` and timestamp. REST PR detail is a possible per-PR metadata source, with extra requests that the rank collector avoids. [GraphQL pull requests](https://docs.github.com/en/graphql/reference/pulls) · [GraphQL issues](https://docs.github.com/en/graphql/reference/issues) · [REST pull requests](https://docs.github.com/en/rest/pulls/pulls)
- `User.contributionsCollection` scopes activity to the viewer and interval. The user review connection returns the most recently submitted review per reviewed PR. Authored PR contributions enumerate opened PRs and can miss older PRs that receive outcomes within the current period. V3.2 uses those observations as bounds and adds independently merged authored PRs discovered in search by stable ID. [GraphQL users](https://docs.github.com/en/graphql/reference/users)
- GitHub documents `author:`, `reviewed-by:`, `involves:`, `repo:`, `org:`, `is:merged`, `is:public` and `merged:`. These narrow discovery and cannot establish who merged a PR. Production does not rely on a merger search qualifier. GraphQL `search(type: ISSUE)` with `is:pr` returns PR candidates. Use cursor pagination and provider caps; GitHub documents a 1,000-result limit for search. The app takes one small sample per alias. [Search qualifiers](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests) · [GraphQL search](https://docs.github.com/en/graphql/reference/search) · [REST search](https://docs.github.com/en/rest/search/search) · [GraphQL pagination](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api)
- Candidates, issue closure evidence and repo metadata are filtered to public repositories. Repo IDs survive renames. An organization-owned repo and an individually owned repo follow the same rules. Private or inaccessible outcomes can be absent even when search reports no next page. [GraphQL repositories](https://docs.github.com/en/graphql/reference/repos) · [GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api) · [REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

## Bounded request plan

1. The existing authenticated profile operation includes merge metadata on reviewed PRs when 3.2 is enabled. The existing score-aware detail page can include this metadata for a second page of user-level reviews.
2. If the shared role or issue outcome can still increase, the planner can schedule one search operation within the existing profile request, points, concurrency and deadline limits. It takes up to 30 involvement candidates, or authored candidates when only issue resolution is uncertain. When integration could still help, up to two public repositories with multiple reviewed PRs can each supply up to 12 more candidates in the same operation. Inspect up to three potentially closed issues on each candidate. No broad repository or commit traversal runs for ranking.
3. Confirm each returned merge against a human author, merger, public repo and exact timestamp. Candidate search truncation remains diagnostic. Search candidates are cached for five minutes, with a thirty-minute failure fallback scoped by a credential hash, user, day-window, query, and version. A cached sample is still partial evidence. It cannot establish historical completeness.

A live schema probe of a three-record reviewed-PR search returned 114 indexed candidates, three records, one query point, and no schema errors. That probe established query availability, not coverage of historical merger activity.

Webhook capture could observe future `pull_request` merged events from repositories granting access. It cannot recover pre-installation history or cover projects outside the installation. No webhook or GitHub App deployment is added here. [Pull request webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads#pull_request)
