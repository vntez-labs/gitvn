# GitVN aggregate collection

The V3.0.0 path ran a default-branch history batch for ranking, sometimes followed by another cursor batch. History may be slower than daily contribution aggregates and differs from profile attribution after rewritten history, co-authorship, date offsets, or contributions on `gh-pages`.

- `User.contributionsCollection(from:to:)` takes inclusive `DateTime` endpoints. The collection exposes the commit, issue, PR, review and created-repository totals, four repository participation totals, its start/end, restricted count and calendar. Restricted counts only describe inaccessible contributions the account shares. Reported totals may include data accessible to the viewer, so compare them to a sum only across equivalent visibility and time scopes. [User schema](https://docs.github.com/en/graphql/reference/users)
- `commitContributionsByRepository(maxRepositories: Int)` returns a list, with 25 documented as the default. GitHub does not document a guaranteed maximum for this argument. Its nested `contributions(first: Int, after: String)` connection returns daily records with `occurredAt`, `commitCount` and `isRestricted`. The generic connection description identifies `totalCount` as a connection total. Live GitHub returned it as the sum of commits for this connection, for example 127 commits across 22 daily nodes. The collector accepts either reconciled interpretation when the cursor reports no next page. [Commit schema](https://docs.github.com/en/graphql/reference/commits) · [User schema](https://docs.github.com/en/graphql/reference/users)
- Follow `pageInfo.hasNextPage` and `endCursor` for connections. GitHub documents a 1–100 page-size range for GraphQL connections. The repository list itself has no cursor. Splitting at midnight UTC uses `23:59:59.999Z` for the previous inclusive end. Deduplicate by stable repo ID and provider date. The live API reports window boundaries at whole-second precision, so boundary comparisons use that precision. [Pagination](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api)
- The user's review connection returns the latest submitted review per reviewed PR. Keep PR and issue identity and confirmed interaction metadata. A closing-reference list indicates potential closure; the score continues to require an observed qualifying close event. [Users](https://docs.github.com/en/graphql/reference/users) · [Pull requests](https://docs.github.com/en/graphql/reference/pulls)
- Observe actual `rateLimit.cost`, `remaining`, `resetAt` and headers. Cost is known after execution; reserve points before starting optional work. Honor server backoff and stop scheduling queries on provider throttling. [GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api) · [REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- Calendar dates use GitHub's attribution rules. GitHub can count work on `gh-pages` and can temporarily retain commits removed by rewriting history. [Profile contributions](https://docs.github.com/en/account-and-profile/reference/profile-contributions-reference) · [Troubleshooting](https://docs.github.com/en/account-and-profile/how-tos/contribution-settings/troubleshooting-missing-contributions)
- REST repository statistics are repository-specific, can return 202 during generation, and are cached against the default branch. They serve optional descriptive analytics. [Repository statistics](https://docs.github.com/en/rest/metrics/statistics)

## Collector 1.0.0 and scoring 3.1.0

- The rank collector reads daily public buckets, using repository IDs for identity. The user totals and repository participation counts describe the annual collection or corroborate its scope. Counts from inaccessible or private repositories stay out of commit and project scoring. The calendar-based consistency metric measures the viewer-visible provider calendar and can include anonymous private contribution activity already present in GitHub's calendar.
- One global daily burst rule applies across repositories. Project qualification uses GitHub-attributed commit counts and observed active dates, or a qualifying merge. It excludes inherited fork commit totals from project eligibility. These metrics are activity proxies. The ranking path does not inspect SHA, content, patch duplication, or empty commits. The descriptive code-lines endpoint retains its own detailed history query.
- The planner begins with an annual query, up to 50 repositories and 100 daily records per repository. It can request one batched continuation for the user-level review, PR and issue connections if their relevant metrics are unresolved. Incomplete commit windows can split to a maximum depth of two, with at least 30 days per child. Complete children replace the corresponding annual dates. Partial children fill gaps, and conflicting partial observations retain the annual value. This preserves observed counts without adding overlapping intervals.
- Defaults reserve a 13-second end-to-end collection window, up to five GraphQL requests including the primary request, up to four optional requests including retries, and one optional request in flight. The 50-point scheduling budget uses actual billed costs plus a conservative preflight reserve, and preserves at least 100 remaining points before scheduling optional work. GitHub determines the actual cost after execution, so the point limit is a scheduling guard rather than a hard provider cap. A transient optional failure can retry once after 150 ms, within the shared deadline. Rate-limit responses stop follow-up work and honor GitHub's retry signal by deferring to a future request; the primary API returns the provider retry hint or a reset-based delay.
- Only monotonic aggregate commit or project metrics can resolve through saturation on a partial enumeration. Bounds use the supported aggregate floor for monotonic metrics and zero for other uncertain metrics. An unresolved metric can contribute up to its configured category weight. Rank resolves when both bounds map to the same tier. These bounds apply to further collection of the same snapshot; provider corrections can change the next evaluation.
- The process-local data cache holds only public commit refinements. Its key includes the GitHub ID, hashed credential scope, UTC evaluation dates, collector and scoring versions, query policy, and annual public evidence. Requests for the same refinement coalesce. Entries are fresh for five minutes and reusable for up to 30 minutes on a failed refresh against identical annual evidence. The primary profile and calendar query still runs so changed visibility, the current window and badges are fetched normally. Scoring output has a separate cache keyed by the actual snapshot and scoring config.
- Incremental refresh could use a recent window and retain previously collected public dates. Historical correctness would require broader rechecks, visibility revalidation, eviction outside the year, and replacement of corrected older buckets. V3.1 uses short-lived annual fingerprinting and replaces verified partitions rather than assuming historical days are immutable.

## Migration

The current route selects collector 1.0.0 and scoring 3.1.0 by default. `GITVN_COLLECTOR_VERSION=3.0` restores the previous V3 collector and scoring semantics. `GITVN_SCORING_V3=0` restores pre-V3 scoring. `GITVN_COLLECTION_ADAPTIVE=0` keeps V3.1 and skips commit partitioning for comparisons. `GITVN_COLLECTION_DIAGNOSTICS=1` emits count and duration diagnostics without identities, repository names or credentials.

## Authenticated comparison

Run the production build, then `node scripts/scoring-collection-benchmark.mjs` with GitHub CLI authorization. The script uses a common evaluation timestamp and credential scope for each comparison and counts actually returned history records, including records that were not reconciled. There is one sample per profile and path, plus a warm repeat for the first profile. Wall time includes the loopback route and upstream network. It is not a latency percentile.

REST profile requests stayed at three for the authenticated user's own profile and two for the other profile. The badge HTML request stayed separate. The live responses returned four and three badges respectively. Both live annual aggregate enumerations reconciled after accounting for the provider's nested total semantics, so the adaptive planner skipped partition requests. Warm refinement and stale fallback are measured separately below.


On the same evaluation window, the provider calendar had **43 active columns** for hnamhocit. Regrouping those same calendar dates into Monday-start UTC weeks produced **40 active weeks**. The V3.0 scorer produced **32** from its narrower activity evidence (public daily commit records and accepted PR, issue and review evidence). The reproduced difference has two sources: the calendar adds provider-visible activity beyond the scorer's evidence set, and the week grouping changes the number of active groups. The public calendar response alone cannot attribute the entire difference to a particular activity type or private activity.

On the hnamhocit sample, all scoring metrics resolved under the new definition. Both score bounds were **61.78**, within **Cao thủ**. The API still reported restricted contributions separately. An earlier instrumented run misread the nested total as the number of days, which caused three unnecessary partition requests. The final collector accepts the live count semantics when all pages agree. Octocat resolved exactly at **18.58** in all three paths. The observed score change reflects the new aggregate and calendar rules. Thresholds and weights remain unchanged.

### Cache-path smoke measurements

A synthetic production-server fixture forces incomplete annual enumeration, a transient 503 on a partition, a warm repeat, and a later refresh blocked by the remaining-point floor. The fixture also changes the credential to verify cache isolation. One measured run took 182 ms adaptive cold, 12 ms warm, and 13 ms for stale fallback, all on loopback with the simulated provider. The cold case includes the 150 ms retry backoff. These times measure planner and route behavior under controlled conditions, not GitHub network latency.
